> 对应代码：RabbitConfig、MqConstants、SeckillOrderSender、SeckillOrderListener、SeckillOrderDlxListener、OrderDelaySender、OrderCloseListener、两个 message 类、MqConsumeLog(Mapper)、application-dev.yml。

## 1. RabbitMQ 拓扑全景（要能默画）

项目有**两条独立的消息链路**，复用同一个死信机制但目的完全不同：

### 链路一：订单超时关单（TTL + DLX 当延迟队列用）

```
订单创建成功（事务提交后）
   │ OrderDelaySender.sendDelayClose()
   ▼
┌─────────────────────────────────────────────┐
│ order.delay.queue                           │
│  参数：x-message-ttl = 60000ms（60秒，无消费者）│
│       x-dead-letter-exchange = order.close.exchange
│       x-dead-letter-routing-key = order.close.rk
└─────────────────┬───────────────────────────┘
                  │ 消息躺 60s 过期，变成"死信"
                  ▼
        order.close.exchange (Direct, 持久化)
                  │ rk = order.close.rk
                  ▼
        order.close.queue (durable)
                  │ OrderCloseListener
                  ▼
   closeExpiredOrder：CAS 关单 + 回补库存
```

### 链路二：秒杀异步下单（MQ 削峰 + DLX 做失败兜底）

```
Redis Lua 预减成功
   │ SeckillOrderSender
   ▼
seckill.order.exchange (Direct, 持久化)
   │ rk = seckill.order.rk
   ▼
┌─────────────────────────────────────────────┐
│ seckill.order.queue (durable)               │
│  参数：x-dead-letter-exchange = seckill.order.dlx.exchange
│       x-dead-letter-routing-key = seckill.order.dlx.rk
│  消费者：SeckillOrderListener（手动ACK）       │
└──────┬───────────────────────────┬──────────┘
  成功 │ basicAck              失败 │ basicNack(requeue=false)
       ▼                           ▼
   订单落库            seckill.order.dlx.exchange
                                   │
                                   ▼
                       seckill.order.dlx.queue
                                   │ SeckillOrderDlxListener
                                   ▼
                       记录 x-death 原因 + 告警 + ACK
```

**面试一句话区分**："链路一的 DLX 是**刻意利用**死信做延迟（消息活到 TTL 自然过期）；链路二的 DLX 是**异常兜底**（消费被拒绝才进入）。同一个机制，两个用途。"

## 2. 消息怎么保证不丢（生产者 → Broker → 消费者 三段论）

这是 MQ 最经典的考题，按三段背，每段项目里都有对应配置。

### 2.1 生产者 → Broker：发送确认

application-dev.yml：

```yaml
publisher-confirm-type: correlated   # 异步 confirm 回调
publisher-returns: true              # 不可达时退回
template.mandatory: true              # 消息路由不到队列时触发 return，而不是默默丢弃
```

RabbitConfig 中 RabbitTemplate 注册了两个回调：

```java
// 消息是否到达 Exchange（broker 处理结果）
setConfirmCallback((correlationData, ack, cause) -> {
    ack=true  → 投递成功
    ack=false → 投递失败，记 error 日志（生产可在此重试/落库补偿）
});
// mandatory 消息无法被路由到任何 Queue
setReturnsCallback(returned → 记 error：exchange/routingKey/原因/消息体);
```

- **confirm 确认的是"消息到了 Exchange 并被处理"**；**return 确认的是"Exchange 没能路由到 Queue"**。两者监控不同阶段。
- `CorrelationData` 携带业务标识（项目用 `userId:skuId:nanoTime`），回调时能对应到具体消息。

### 2.2 Broker 自身：持久化

三个持久化手段（缺一不可）：

1. **Exchange 持久化**：`new DirectExchange(name, true, false)`——第二个参数 durable=true
2. **Queue 持久化**：`QueueBuilder.durable(name)`——RabbitMQ 重启后队列定义还在
3. **消息持久化**：Spring AMQP 默认消息投递模式就是 PERSISTENT（消息属性 deliveryMode=2），配合持久化队列，重启不丢

注意：持久化是"先写盘再对外确认"，有性能损耗但保可靠。极端情况下（写盘了但 confirm 还没发回，broker 宕机）理论上仍可能丢，要求绝对可靠可用镜像队列/仲裁队列（Quorum Queue，基于 Raft）。

### 2.3 Broker → 消费者：手动 ACK

```yaml
listener.simple.acknowledge-mode: manual
prefetch: 10
```

消费者代码（SeckillOrderListener）：

```java
try {
    seckillService.handleSeckillOrder(message);  // 业务处理+DB事务
    channel.basicAck(deliveryTag, false);         // 成功才确认
} catch (Exception e) {
    补偿 Redis 库存;
    channel.basicNack(deliveryTag, false, false); // 失败不确认;requeue=false → 进DLQ
}
```

**为什么必须手动 ACK**：自动 ACK 模式下消息一投递就算消费成功，业务还没执行完应用崩了，消息就丢了。手动 ACK 把"确认时机"掌握在业务成功之后。

**prefetch=10 的意义**：RabbitMQ 一次最多推 10 条未确认消息给一个消费者，防止慢消费者被消息压垮，也让队列在多个消费者间均匀分配（能者多劳）。

### 2.4 nack 的第三个参数为什么是 false（requeue）

- `requeue=true`：消息重新入队立刻再投递给消费者。如果失败是**消息本身的问题**（毒消息，如数据残缺），会形成"投递→失败→重回→再投递"的无限循环，打满 CPU，消息永远过不去。
- `requeue=false`：消息不重回原队列，而是按队列配置的 DLX 进入死信队列，链路保持畅通，问题消息被隔离等待人工处理。

## 3. 消息怎么保证不重复（幂等性专题）

### 3.1 先承认事实：MQ 的"恰好一次"很难

网络抖动时会出现：消费者处理完业务但 ACK 没发到 Broker → Broker 认为没消费 → 重投。所以**重复投递是常态，工程解法是消费端幂等**，而不是追求绝对不重复（At-least-once + 幂等 = Effectively-once）。

### 3.2 项目的幂等方案：mq_consume_log 表

SQL（09-mq-schema.sql）核心：

```sql
CREATE TABLE mq_consume_log (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  message_id VARCHAR(64) NOT NULL,
  queue_name VARCHAR(64) NOT NULL,
  ...
  UNIQUE KEY uk_message_id (message_id)
);
```

Mapper 的 tryConsume：

```sql
INSERT IGNORE INTO mq_consume_log(message_id, queue_name, ...) VALUES(?,?,...)
```

消费入口（handleSeckillOrder / closeExpiredOrder 都在第一行）：

```java
if (mqConsumeLogMapper.tryConsume(messageId, queue) == 0) {
    // 插入被唯一索引拒绝(影响行数0) → 这条消息处理过
    return;
}
```

**为什么用 INSERT IGNORE 而不是先 SELECT 再 INSERT**：先查后插不是原子的，两个并发的相同消息可能都查到"没有"再各自插入、各自执行业务。INSERT IGNORE 由数据库唯一索引保证：**只有一个线程能插入成功（返回1），其余全部返回0**。

### 3.3 高频追问：日志写入和业务在同一事务内，提交/回滚分别怎样

这是项目里非常精妙的设计，要讲清两种情况：

```
业务成功 → 事务提交 → mq_consume_log 记录留存
                      后续重投：INSERT IGNORE 失败 → 幂等跳过 ✓

业务抛异常 → 事务回滚 → mq_consume_log 记录一起回滚！
                      消息重投时可以重新插入、重新执行业务 ✓（允许重试）
```

如果日志写入在独立事务（提前提交），业务失败后日志留下了，重投时被误判为已消费，消息再也不会被处理——这是常见错误。**同一事务保证"业务没成功 = 消费记录不存在"**。

### 3.4 幂等的多层体系（秒杀消费）

项目不是只靠一张表，而是纵深三层：

| 层 | 机制 | 维度 |
|---|---|---|
| 1 | mq_consume_log（messageId 唯一） | 消息维度，防同一条消息重投 |
| 2 | 查询 sms_seckill_order 是否已存在（userId+seckillSkuId） | 业务维度，防不同消息造成同效果 |
| 3 | DB 唯一索引 uk_user_sku | 数据库最终约束，兜底 |

另外普通下单入口还有**令牌幂等**（Redis Lua GET+DEL，见文档二），那是防用户重复提交，与 MQ 幂等互补。

### 3.5 幂等通用手段总结（面试可扩展）

- 唯一索引（本项目）
- 去重表（mq_consume_log 本质就是）
- 状态机条件更新（订单 `UPDATE ... WHERE status=前置状态`，重复支付影响行数 0）
- 乐观锁版本号
- 分布式锁（Redisson 串行）

## 4. 死信队列（DLX）完整知识

### 4.1 一条消息变成死信的三种原因

1. 被消费者 **basicReject/basicNack 且 requeue=false**（秒杀失败走这个）
2. **消息 TTL 过期**（订单延迟关单走这个）
3. 队列达到最大长度（x-max-length）被挤出

进入死信时消息会带上 **x-death** 头部，记录原队列、交换机、死信原因、时间、次数等。SeckillOrderDlxListener 正是读这个 header：

```java
@Header(value="x-death", required=false) List<Map<String,Object>> xDeath
String reason = xDeath.get(0).get("reason");   // 如 rejected / expired
```

### 4.2 死信消费者的处理策略及取舍

SeckillOrderDlxListener 的做法：**记录详情 + 告警（预留接入点）+ 直接 ACK**。

为什么 ACK 而不是再处理：
- 消息已经失败过一次，原问题大概率还在，自动重试只会循环
- DLQ 的定位是"隔离 + 留证 + 人工介入"，不是自动恢复
- 即使死信处理自身抛异常也 ACK（第49-53行），防止 DLQ 自己出现毒消息循环

代码中预留了两个生产化方向（TODO）：
- 接入钉钉/飞书 Webhook 告警
- 管理端提供"重试"按钮，人工确认后把消息重新投递回 seckill.order.queue

### 4.3 为什么不用延迟插件而用 TTL+DLX

- TTL+DLX 是 RabbitMQ 原生能力，**无需安装 rabbitmq_delayed_message_exchange 插件**，部署简单
- 本项目订单超时时间统一（60s），用队列级 TTL 最合适
- 队列级 TTL 的注意点（要知道）：**队头阻塞**——队列里先入队的消息 TTL 长，会挡住后面已过期的消息，过期消息要等前面消息出队后才被投递。若每单超时不同，改用消息级 expiration 时尤其明显。本项目所有订单 TTL 一致，没有此问题。

### 4.4 关单消费者失败为什么没有再配 DLQ（对比）

OrderCloseListener 失败时也是 nack requeue=false，但 order.close.queue 没有配 DLX——消息会被丢弃。这是**可接受的**：关单失败不影响正确性，订单状态不变（仍待支付），用户支付后正常走支付流程；且关单是兜底操作不是关键路径。生产环境可以再补一层异常队列。被问到时如实分析这个取舍即可。

## 5. 秒杀的分布式一致性设计（面试最硬核部分）

### 5.1 先讲清楚：这里"分布式事务"发生在哪

秒杀下单涉及两个独立系统的状态：

```
Redis 库存（seckill:stock / ordered集合）  ←→  MySQL（订单 + DB库存）
```

它们无法用一个本地事务同时更新，所以存在一致性问题。

### 5.2 为什么不用 Seata AT / 2PC（必答）

| 方案 | 为什么不适合秒杀 |
|---|---|
| 2PC / Seata AT | 同步阻塞，prepare/commit 两阶段把锁持有时间拉长，秒杀高并发下吞吐骤降 |
| Seata AT | 需要给每个参与表加 undo_log、靠全局锁保证读隔离，对 Redis（非 JDBC 资源）支持也不直接；架构重 |
| XA | 资源锁定周期长，性能最差 |

**核心判断**：秒杀场景**允许极短时间的不一致和个别请求失败**，要求的是**高吞吐 + 最终一致**，而不是所有参与者实时强一致。这是业务特性决定的选型。

### 5.3 项目的四层一致性防御（替代分布式事务）

```
第1层：Redis Lua 原子预减
       一人一单 + 库存预减一次调用完成，Redis 侧绝不超卖

第2层：本地事务落库
       DB条件扣库存 + 订单/明细/秒杀订单 同一个 @Transactional
       要么全成功要么全回滚（DB 内部 ACID 保证）

第3层：失败补偿
       消费抛异常 → 归还 Redis 库存、移除已购标记、写 FAIL、清售罄标记
       用户可重新抢购，Redis 与 DB 重新对齐

第4层：死信隔离 + 人工兜底
       自动补偿也失败的异常消息进 DLQ 留证，人工排查重试，不静默丢失
```

加上两个细节：
- **afterCommit 发结果**：只有 DB 事务真正提交，才写 SUCCESS 结果和成功指标，杜绝"回滚了但用户看到成功"
- **DB 条件扣减是最终防线**：即使 Redis 因故障给出错误的成功，`UPDATE ... WHERE seckill_stock>=1` 也保证 DB 不会超卖

### 5.4 逐场景分析失败矩阵（面试官最爱，务必熟练）

| 故障点 | 会发生什么 | 系统怎么处理 |
|---|---|---|
| Lua 成功，应用在发 MQ 前崩溃 | Redis 库存少了 1、用户被标记已购，但无订单 | **本项目最薄弱点**：MQ 发送在 Lua 之后。消息根本没产生，DLQ 也无能为力，Redis 与 DB 短暂不一致。用户端一直 QUEUING，最终结果 key 过期 |
| ↑ 生产级修法 | 要能说出：① 把"本地消息表 + 定时对账"补上（预减成功先落一条本地记录，事务性发件箱模式 Outbox，定时任务扫描未确认记录补偿）；② 对账任务比对 Redis 已购集合与 DB 订单，对有标记无订单的归还库存/补发消息；③ 前端轮询超时（如30s）后主动提示失败并触发归还 |
| MQ 发出，Broker 还没落盘就宕机 | 消息丢失 | publisher confirm 回调 nack/超时 → 本地记录可重发；持久化 + 仲裁队列降低概率 |
| 消费者处理完 DB，ACK 前崩溃 | 订单已落库，Broker 重投同一消息 | mq_consume_log 唯一索引拦截，幂等跳过；不会重复落单 |
| 消费者处理中 DB 异常 | 事务回滚（DB 无订单，消费日志也回滚） | 补偿 Redis 库存 + nack 进 DLQ + 用户看到 FAIL 可重试 |
| 延迟关单消息到达时用户已支付 | CAS 关单影响行数 0 | 直接跳过，不会关掉已支付订单 |
| 用户取消订单 | 关单/取消并发 | 同一套 CAS，只有一个成功，另一个影响行数0 |
| 消息重复投递 | 业务执行两遍 | messageId 幂等 + 业务唯一索引 |

**讲薄弱点的技巧**：主动承认 + 给出修法 + 说明为何当前可接受（个人项目/演示环境，压测显示概率极低）。能说出 Outbox、对账任务这种改进方案，面试官会认为你有生产思维。

### 5.5 本地消息表 / Outbox 模式（必会的改进方案）

原理：把"要发的消息"先写进**与业务同一个数据库事务**的本地消息表：

```
BEGIN;
  UPDATE stock ...;
  INSERT orders ...;
  INSERT local_message(id, payload, status='待发送');  -- 与业务同事务
COMMIT;
        ↓
独立的发送线程/定时任务扫描 status=待发送 的记录
  → 发 MQ → 收到 publisher confirm → 改 status=已发送
  → 失败就重试（消息有 messageId，消费端幂等，重试安全）
```

它把"业务成功但消息没发出"的跨系统问题，转化成"对同一个数据库的本地事务 + 可靠重试"，是业界最常用的最终一致方案之一。与 mq_consume_log（消费端）对称，一个管发、一个管收。

## 6. 其他 MQ 八股联动

1. **为什么用 MQ**：解耦（订单系统不直接调用一堆下游）、异步（秒杀先返回）、削峰（瞬时流量摊平）。
2. **引入 MQ 的代价**：系统可用性降低（Broker 挂了链路断）、复杂度上升（丢消息/重复/顺序/一致性）、延迟可能增加。要主动说代价显得成熟。
3. **顺序消息**：秒杀场景不需要全局顺序；若需要（如同一订单的创建/支付消息），用单个队列单消费者，或按业务 key 分区路由（同一 key 进同一队列）。
4. **消息积压怎么处理**：扩消费者实例、临时改批量消费、排查下游慢节点；根本上保证生产/消费速率匹配（本项目压测验证消费600 ≥ 生产约480，零堆积）。
5. **RabbitMQ vs Kafka**：RabbitMQ 路由灵活、确认机制完善、延迟低，适合业务消息；Kafka 吞吐极高、顺序写盘、适合日志/流处理。秒杀业务消息量级用 RabbitMQ 足够且更好管控可靠性。
6. **Exchange 四种类型**：Direct（routing key 精确匹配，项目全用它）、Fanout（广播）、Topic（模式匹配）、Headers（按头匹配）。
7. **vhost**：RabbitMQ 的逻辑隔离（项目用默认 `/`），不同应用可隔离权限与资源。
