# 07 交易中台面试问答（P0–P5 升级专项）

> 前提：项目从「单体秒杀系统」升级为「交易中台」，新增 Nacos/Sentinel、RocketMQ 事务消息、ShardingSphere 分库分表、Elasticsearch 搜索，并完成 2k+ QPS 压测与优化。
> 本文只回答**这次升级引入的问题**，Redis/Lua/JWT/缓存等基础题见 [04-面试高频问答](04-面试高频问答.md)。
> 标注 ⭐ 的为必背；所有数字来自 [benchmark-report-v2.md](../benchmark-report-v2.md)。

---

## 1. 升级动机与整体设计

### ⭐ 1.1 为什么叫「交易中台」而不是「秒杀系统」？

三个变化：

1. **下单链路从同步/半同步变为异步最终一致**：引入 RocketMQ 事务消息，把「扣库存」和「生成订单」解耦到两个进程边界，系统从"抢购接口"变成"交易受理 + 交易履约"。
2. **订单域独立分库分表**：订单表按用户维度拆到 ds1/ds2 共 8 个分片，交易域与商品/用户域物理隔离，具备横向扩容能力。
3. **具备治理与可观测闭环**：Nacos 注册/配置、Sentinel 热点限流、ES 检索、Prometheus + Zipkin，能对流量做管控、对链路做定位。

一句话：**秒杀是入口能力，交易中台是"承接流量 → 保证不超卖不重复 → 异步履约 → 可治理可观测"的完整链路。**

### 1.2 升级分了哪几个阶段，为什么这么排？

| 阶段 | 内容 | 排序理由 |
|---|---|---|
| P0 | 环境重建 + 基线压测 | 没有基线就无法证明优化有效 |
| P1 | Nacos + Sentinel | 先有"能观测、能限流"的底座，后面压测才不会把宿主打爆 |
| P2 | RocketMQ 事务消息 | 交易一致性的核心，改动最大，放在分库前做便于回归 |
| P3 | ShardingSphere 分库分表 | 依赖 P2 的消费链路，必须做完整回归 |
| P4 | ES + IK 搜索 | 与交易链路解耦，可并行但放后面避免干扰压测 |
| P5 | 压测与优化 | 前面所有改动完成后统一测，避免反复重建基线 |

每个阶段都有独立脚本（`scripts/phase1~4-verify.ps1`、`phase0-baseline.ps1`、`phase5-bench.ps1`、`phase7-smoke.ps1`），以脚本结尾的 `*_OK` / `*_DONE` 标记判定成功（如 `P2_OK`、`SMOKE_OK`、`P5_BENCH_DONE`）。

### 1.3 升级过程中最大的取舍是什么？

**4 实例扩容失败回退 2 实例。** 设计上想横向扩容，实测 reject c=200 从 2222 掉到 1081 QPS，且首轮出现 601 个 5s 超时——宿主 8 核、Docker VM 11.68GB、空闲内存仅约 0.4~0.7GB，4 个 JVM 争抢 CPU 与页缓存，负收益。结论：**扩容不是无条件的，受宿主资源与共享中间件约束**；同时把「本地售罄标记」改成带 TTL，保证多实例下补货能自愈。

## 2. Nacos 与 Sentinel

### ⭐ 2.1 为什么用 Nacos 同时做注册中心和配置中心？

- 注册：双实例注册为 `mall-seckill-app`，Nginx 之外还有服务发现能力（后续可换 Spring Cloud LoadBalancer/Gateway）。
- 配置：`spring.config.import: optional:nacos:mall-seckill.yaml`，Nacos 不可用时仍可用本地默认值启动——**降级不阻塞启动**是关键取舍。
- Sentinel 规则也存 Nacos（`SENTINEL_GROUP` 下 `*-flow-rules.json`、`*-degrade-rules.json`、`*-param-flow-rules.json`），应用启动自动拉取，控制台改动持久化，重启不丢。

### ⭐ 2.2 Sentinel 在这里限的是什么？为什么用热点参数限流？

- 资源：`@SentinelResource("seckillExecute")` 打在抢购接口上，`blockHandler` 统一返回限流响应。
- 规则：热点参数（按 `seckillSkuId`）2000 QPS/实例——**不同秒杀商品互不影响**，热点商品单独限流，避免一个爆款拖垮全站。
- 为什么不用普通 QPS 限流：普通限流是接口级的，会把冷门商品一起限掉；热点参数按参数维度统计，粒度更贴合秒杀场景。
- 与 `@AccessLimit` 的分工：`@AccessLimit` 是 Redis ZSet 滑动窗口的**用户级**限流（防刷），Sentinel 是**系统级**保护（防打爆），两层互补。

### 2.3 Sentinel 和 Hystrix 的区别？

Sentinel 以"流量"为核心（QPS/并发/热点/系统自适应），有控制台和规则动态推送；Hystrix 以"线程池隔离 + 熔断"为核心，已停止维护。Spring Cloud Alibaba 体系下选 Sentinel 是默认答案。

### 2.4 Nacos 挂了会怎样？

- 配置：`optional:nacos:` 前缀，拉不到就用本地 `application-prod.yml` 默认值，应用可启动。
- 注册：已注册实例短时间仍可用（客户端有本地缓存），但新实例无法发现，Nginx 静态 upstream 不受影响。
- Sentinel 规则：本地内存已加载的规则继续生效，只是不能热更新。

## 3. RocketMQ 事务消息

### ⭐ 3.1 事务消息解决什么问题？和之前 afterCommit 方案的区别？

之前：DB/Redis 本地事务提交后，`afterCommit` 再发 MQ。存在「**本地事务已提交、消息未发出、进程宕机**」的窗口，消息永久丢失。

事务消息：

```
① 发送半消息（Broker 存储，消费者不可见）
② 执行本地事务（Redis Lua 预减 + 一人一单，结果写 Redis 标记，TTL 1h）
③ 返回 COMMIT / ROLLBACK
④ Broker 若长时间未收到二次确认 → 回查 checkLocalTransaction（读 Redis 标记）
```

- 本地事务成功 → COMMIT → 消费端落单
- 售罄 / 一人一单命中 → ROLLBACK → 半消息丢弃，不产生订单
- 进程在 ②③ 之间宕机 → Broker 回查，按 Redis 标记决定提交或回滚

**核心差异：消息的"最终命运"由本地事务结果决定，而不是"发出去就发出去"。**

### ⭐ 3.2 回查为什么要用 Redis 标记，而不是查 DB？

- 本地事务是 **Redis Lua 预减**，不是 DB 事务，DB 里此时没有可判断的记录；
- 回查必须快速且幂等，Redis 一次 `GET` 即可（`tx-result:{userId}:{skuId}`，TTL 1h）；
- 标记有 TTL，避免无限增长；超过回查窗口（默认 15 次）仍未确认的，Broker 丢弃半消息。

### ⭐ 3.3 事务消息能保证"一定不丢"吗？

不能 100% 保证，需要分情况：

| 故障点 | 行为 | 结果 |
|---|---|---|
| ② 执行前宕机 | 半消息未确认 | 回查发现无标记 → ROLLBACK |
| ② 执行后、③ 前宕机 | 回查发现 COMMIT 标记 | 提交，正常落单 |
| Broker 全挂 | 半消息未持久化成功 | 发送失败，本地事务不执行，接口返回失败，用户可重试 |
| 消费端反复失败 | 重试 16 次后进 DLQ | 告警 + 人工/定时对账 |

真正的兜底是**对账**：Redis 已购集合 vs DB 订单表，差异单补单或回补库存。

### 3.4 消费端如何保证幂等？

`mq_consume_log`（`message_id` 唯一索引）`INSERT IGNORE`，返回 0 直接 ACK。日志写入与业务处理在**同一事务**：业务成功则日志留存，业务回滚则日志一起回滚、允许重试。

### 3.5 事务消息 vs Outbox vs Seata AT，怎么选？

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|---|---|---|---|---|
| RocketMQ 事务消息 | 最终一致（含回查补发） | 高（异步） | 中 | 秒杀、订单创建等"允许秒级收敛"的场景 |
| Outbox 本地消息表 | 最终一致（本地事务保证必发） | 中（多一次表写 + 扫描） | 中 | 消息绝对不能丢、MQ 不支持事务消息 |
| Seata AT | 强一致（全局锁） | 低 | 高 | 转账、扣款等不容错场景 |

秒杀的业务语义是"抢不到可接受、最终成功即可"，所以选事务消息，不选 Seata。

### 3.6 半消息发送超时或本地事务未执行，接口返回什么？

`dispatch` 内 `context.getStatus() == null` 判定"本地事务未执行"，返回 `UNKNOWN`，接口层按失败处理（不返回排队中），避免前端无限轮询。日志打 `warn` 并带 `sendStatus` 便于排查。

## 4. ShardingSphere 分库分表

### ⭐ 4.1 分片键为什么选 user_id，路由算法怎么设计？

- 订单查询 90% 是"我的订单"，按 `user_id` 分片可命中单分片；
- 库：`ds${user_id % 2 + 1}` → ds1/ds2；表：`(user_id >> 1) % 4` → 0~3；
- 组合后共 8 个分片，`user_id` 连续的两个用户会落到不同库，避免单库热点；
- 明细表 `oms_order_item`、关联表 `sms_seckill_order` 用**同一路由表达式**，保证订单主表/明细/秒杀关联永远同槽位，避免跨库 JOIN。

### ⭐ 4.2 跨库事务怎么保证？为什么用 XA？

下单要写 `oms_order` + `oms_order_item` + `sms_seckill_order` + 扣减主库库存，参与者跨 ds0/ds1/ds2。用 ShardingSphere 的 XA + Atomikos 两阶段提交，保证跨库原子性。

代价：每个订单 2PC 有 prepare/commit 两轮网络交互 + 事务日志落盘，这是 P5 成功路径 CPU 高的主要原因之一（见 6.6）。

### 4.3 XA 的缺点是什么？怎么优化？

- 同步阻塞、持锁时间长、协调者宕机有悬挂风险、性能约为本地事务的 1/2~1/3；
- 优化方向：① 把订单/明细/关联表做到同库同表（消除跨库）；② 改用"本地事务 + 事务消息"的最终一致（订单落库与库存扣减解耦）；③ 只对关键表用 XA，非关键表用本地事务 + 补偿。

### 4.4 分片后分页、聚合查询怎么办？

- 深分页：ShardingSphere 会把 `LIMIT offset, size` 改写为各分片 `LIMIT 0, offset+size` 再归并，offset 越大越慢；
- 优化：游标分页（`WHERE id < lastId ORDER BY id DESC LIMIT n`）或把列表查询放 ES；
- 跨分片聚合（如全场销量）：走 ES 或离线汇总表，禁止在交易库做全分片 `SUM`。

### 4.5 分片扩容怎么做？

当前 `user_id % 2` / `(user_id >> 1) % 4` 是固定模。扩容到 4 库时路由变化会导致**全量数据迁移**。生产做法：
1. 双写新老分片 + 增量同步 + 校验后切读；
2. 或改用一致性哈希 / 基因法（把分片位编码进订单号），减少迁移量。

### 4.6 为什么 `sms_seckill_order` 也要分片？

它承载"一人一单"的 `uk_user_sku` 唯一索引，如果留在主库，下单时就要跨库写两个事务参与者，XA 成本更高；分片到与订单同槽位后，一次 2PC 只涉及订单库 + 库存主库。

## 5. Elasticsearch 搜索

### ⭐ 5.1 为什么引入 ES？MySQL LIKE 不够吗？

- `LIKE '%关键词%'` 无法走索引，全表扫描；中文分词、相关度排序、高亮都做不了；
- ES 倒排索引 + IK 分词支持中文检索、`multi_match` 相关度、`highlight` 高亮、聚合筛选（分类/价格）；
- 商品数据是"读多写少"，适合放到搜索引擎。

### ⭐ 5.2 索引如何与 MySQL 同步？

- **增量**：商品增删改时把 SPU ID 写入 Redis 脏集合，定时任务批量拉取 → 更新 ES → 移除脏标记；
- **补偿**：定时全量/差异对账（`POST /api/admin/search/reindex` 可手动全量重建）；
- 为什么不用 Canal/binlog：项目规模小，减少一个组件依赖；生产可用 Canal 做准实时。

### 5.3 ES 挂了怎么办？

搜索服务捕获异常后**自动降级 DB 分页查询**（`LIKE` + 分类过滤），保证功能可用，只是相关度和性能下降。降级发生在服务层，Controller 无感知。

### 5.4 IK 分词器的作用？

`ik_max_word` 建索引（细粒度，召回高），`ik_smart` 查询（粗粒度，准确）；相比默认 standard 分词器，能正确切分"华为手机""运动鞋"等中文词组。

### 5.5 深分页怎么处理？

ES 默认 `from+size` 上限 10000。方案：`search_after` + 排序游标（推荐）、`scroll`（导出场景，占用上下文）、或限制最大页码。

## 6. P5 压测与性能优化

### ⭐ 6.1 压测方法是什么？为什么客户端要跑在容器里？

- 客户端 `SeckillBench.java` 运行在 `maven:3.9-eclipse-temurin-21` 容器内，接入 `mall-seckill_mall-net`，直连 `http://nginx`；
- 原因：Windows → Docker 的端口转发在千级 QPS 下本身就是瓶颈（连接排队、NAT 开销），会把服务端能力测低；
- 四种模式：`reject`（售罄拒绝，固定 token）、`success`（一人一单，批量注册用户 + 并发换路径）、`seed`（造用户）、`raw`（任意 URL，用于分离基础设施开销）；
- 指标：QPS、`ok/rejected/limited/errors`、p50/p95/p99、max。

### ⭐ 6.2 优化前后的关键数据？

| 场景 | P0 基线 | P5 优化后 |
|---|---|---|
| 售罄拒绝 c=100 | 787 | 2539（峰值） |
| 售罄拒绝 c=200 | — | 2222 |
| 售罄拒绝 c=400 | 555（22 个网络错误） | 1128~1334（0 错误） |
| 成功下单 c=200 | — | 1013（峰值）/ 847（中位） |
| 错误率 | 0.44% | <0.01% |

### ⭐ 6.3 做了哪些优化？每条优化省掉了什么？

| 优化 | 省掉的开销 |
|---|---|
| 本地售罄标记前移到第 1 步 | 拒绝路径 1 次 Redis `GET`；售罄后 0 次 Redis 往返 |
| 售罄标记加 TTL 10s | 不省开销，解决多实例补货后误拒（正确性） |
| 秒杀商品信息 Caffeine 5s | 2 次 Redis 往返（场次索引 + hash 详情） |
| 认证信息 Caffeine 30s | 每请求 3 次 DB 查询（用户 + 角色 + 权限） |
| Lua 内合并删除结果 key | 1 次 Redis `DEL` |
| 热路径 INFO → debug | 每单 4 条日志写 Docker json-file 的 IO |
| Nginx `access_log off` + 4 worker + keepalive 128 | 日志串行化 + 连接建立开销，1289 → 1.6k+ |

### ⭐ 6.4 为什么本地售罄标记必须加 TTL？

多实例下，补货只能清掉"处理补货请求的那台实例"的内存标记，另一台仍认为售罄，持续误拒。加 10s TTL 后，其余实例最迟 10s 自动恢复；压测脚本用「连续 4 次预热 + 等 11s」规避这一窗口。

### 6.5 售罄拒绝路径的瓶颈最终在哪？

业务侧已经没有 Redis 往返，压测显示 app CPU < 5%。瓶颈在 **Nginx（Docker Desktop 单 VM）+ 压测客户端**，同一配置跨轮次 1063~2539 QPS 波动，主因是宿主空闲内存仅约 0.4~0.7GB 带来的换页与调度抖动。

### ⭐ 6.6 成功路径为什么只有 ~1000 QPS？

`docker stats` 采样：压测时 app1/app2 各 **300~360% CPU**（合计约 6.5/8 核），broker 8%、Redis 1~4%。原因：

1. 同一 JVM **既发事务消息又消费**，生产与消费争抢 CPU；
2. 消费端 **Atomikos XA 两阶段提交**要写 3 个 MySQL（订单库 2 个 + 主库），包含 prepare/commit 与事务日志；
3. 每单还有 Redisson 锁、`selectCount` 一人一单校验、SKU/SPU 查询、三表插入。

继续提升的路径：拆分 consumer 进程、减少 XA 参与方（把关联表/明细同库）、增加异步批量落库。

### ⭐ 6.7 p99 < 150ms 和 1000 QPS 为什么不可兼得？

- c=100 时 p50 58.9ms、p99 142ms，但 QPS 只有 592；
- c=200 时吞吐上到 1013，但 CPU 打满，p50 158ms、p99 412~666ms；
- 本质是排队论：服务时间 ~1ms 量级 + 宿主 CPU 饱和，并发越高队列越长，p99 必然抬升。要同时满足需水平扩容到独立物理机。

### 6.8 数据一致性怎么验证的？

- 8 个分片累计 **27005** 笔秒杀订单，按 `user_id` 聚合重复数 **0**（一人一单约束生效）；
- Redis 预减数量与 DB 扣减数量一致，超时关单后库存正确回补（`order.close.queue` 消费 27003 条验证）；
- 6 万+ 请求中仅 3 个客户端 5s 超时（<0.01%），无 5xx。

### 6.9 压测中有哪些"坑"值得说？

1. **Nginx access_log 写 stdout** 被 Docker json-file 串行化，关掉后 1289 → 1684；
2. **只预热一台实例**导致另一台仍带售罄标记，1000 个请求 499 被拒 → 引入 TTL + 多次预热；
3. **4 实例扩容**因宿主内存不足反而更慢；
4. **`docker cp` 改 nginx.conf** 报 device or resource busy（bind mount 必须改宿主文件）；
5. **Prometheus 只有 summary 没有 histogram**，服务端 p99 无法直接算，改用客户端采集。

## 7. 场景与反问

### 7.1 现在流量再涨 10 倍，你怎么办？

按瓶颈顺序：① 拆分消费者进程/独立部署，消除生产消费争抢；② 订单域减少 XA 参与方或改最终一致；③ Nginx 换 LVS/云 LB，应用无状态水平扩容（本地标记已有 TTL，可安全多实例）；④ Redis 集群化（库存分片 + 热点 key 打散）；⑤ 秒杀入口加答题/预约制削峰。

### 7.2 你这次升级最不满意的地方？

4 实例扩容失败说明我对"资源约束"评估不足；另外成功路径仍在 1000 QPS 边界，XA 的成本是设计时就该预判的。已把结论写进报告，而不是只留一个好看的峰值数字。

### 7.3 如果重做一次，你会怎么调整顺序？

先做「消费进程拆分 + XA 精简」再压测，因为这是结构性瓶颈；本地缓存、日志降级这类微优化放到最后。分库分表如果只为演示，可以先用逻辑分表 + 后续迁移，降低一次性复杂度。
