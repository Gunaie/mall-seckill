# mall-seckill 交易中台升级方案（P0–P6）

> 目标：把「秒杀 Demo」升级为具备交易一致性、数据分片、商品搜索、服务治理与 2k+ QPS 证据链的「交易中台」。
> 本方案按阶段执行，每个阶段有独立验收门槛，验收通过后再进入下一阶段。

---

## 1. 现状与差距

### 1.1 现状基线

| 项 | 现状 |
|---|---|
| 架构 | 单体 Spring Boot 3.2.5，Nginx + app1/app2 双实例 |
| 交易链路 | Redis Lua 预减 + RabbitMQ 异步下单 + MySQL 落单 + afterCommit 发延迟关单 |
| 峰值 QPS | 售罄拒绝 1026（本地标记 ON）/ 476（OFF）；成功下单 738；消费 TPS ~600（双实例） |
| 一致性 | afterCommit 发送 + mq_consume_log 幂等 + DB 条件扣减 + 失败补偿；存在「Lua 已扣、MQ 未发」窗口 |
| 数据层 | 单库 mall_seckill，订单表未分片 |
| 搜索 | MySQL LIKE `pms_spu.name`，无全文检索/相关性/高亮 |
| 治理 | 自研 `@AccessLimit` 滑动窗口；无统一配置中心、无熔断降级/热点参数限流 |
| 可观测 | Prometheus + Grafana + Zipkin 已有 |

### 1.2 目标差距

| 能力 | 目标 |
|---|---|
| 一致性 | RocketMQ 事务消息：半消息 → 本地事务（Redis Lua）→ 提交/回滚 → 事务回查；消费端幂等不变 |
| 分库分表 | 订单域 2 库 × 4 表 = 8 分片，`user_id` 分片键，同用户订单事务落同一物理库 |
| 搜索 | Elasticsearch 8.11.4 + IK 分词，关键词/分类/价格区间/排序/高亮，增量同步 + 全量重建 + 降级回 DB |
| 治理 | Nacos 注册/配置中心 + Sentinel 流控/热点参数/熔断降级，规则持久化到 Nacos |
| 性能 | 秒杀拒绝路径 ≥2000 QPS；成功路径 ≥1000 QPS；错误率 <0.1%；p99 <150ms；不超卖、不重复下单 |
| 交付 | 压测报告含瓶颈定位、优化前后对比、资源水位与复现命令 |

## 3. 技术选型与版本矩阵

| 组件 | 版本 | 说明 |
|---|---|---|
| Spring Boot | 3.2.5 | 不变 |
| Spring Cloud | 2023.0.1 | BOM |
| Spring Cloud Alibaba | 2023.0.1.0 | 与 Boot 3.2.x / Cloud 2023.0.1 对齐 |
| Nacos | 2.4.3 | standalone，内嵌存储；注册 + 配置 |
| Sentinel | 1.8.8 | Dashboard `bladex/sentinel-dashboard:1.8.8` |
| RocketMQ | 5.3.1 | namesrv + broker；事务消息 |
| ShardingSphere-JDBC | 5.5.0 | 订单域分片 |
| Elasticsearch | 8.11.4 | 与 Spring Data Elasticsearch 5.2.x 客户端对齐 |
| IK 分词 | 8.11.4 | 自定义 ES 镜像安装，失败降级 standard |
| MySQL / Redis / RabbitMQ | 8.0 / 7 / 3.13 | 不变 |
| 压测 | `scripts/SeckillBench.java` | 扩展多用户 token 与混合场景 |

### 3.1 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 跨服务一致性 | **RocketMQ 事务消息** | 单体无需拆服务；半消息 + Redis Lua 本地事务 + 回查，直接修补「Lua 已扣、MQ 未发」窗口；比 Seata AT 少一次全局锁与 TC 依赖 |
| Seata | 不落地，只在文档做对比 | 需要拆订单/库存服务 + TC，改造量与资源开销大；秒杀高并发下全局锁会压低吞吐 |
| 延迟关单 | **保留 RabbitMQ TTL + DLX** | 与事务消息职责分离：RocketMQ 保交易一致性，RabbitMQ 保延迟关单；降低一次性改造风险 |
| 分片键 | `user_id` | 买家「我的订单」是主查询；同用户订单/明细/秒杀关联同库，单事务本地 ACID |
| 分片数 | 2 库 × 4 表 = 8 | 满足 2k QPS 与后续扩容演示，容器资源可控 |
| ES 同步 | after-commit 异步 + Redis 脏集合补偿 + 全量重建 | 保证最终一致，ES 故障不阻塞交易主链路 |
| 压测口径 | 售罄拒绝路径 ≥2000 QPS | 与现有基线 1026 可直接对比，最能体现热路径优化 |

### P2 RocketMQ 事务消息（交易一致性）✅ 已完成

> 实施记录（与下方设计的差异）：
> - 事务回查改用 **本地事务结果标记** `seckill:tx:result:{messageId}`（TTL 1h），不再用「已购集合」判定——集合无法区分本次事务是否成功。
> - RabbitMQ 秒杀发送链路未删除，改为 `mall.rocketmq.enabled=false` 时回退（本地开发/单测无需 Broker）；RabbitMQ 保留延迟关单。
> - 消费失败语义：`BusinessException` → 补偿 Redis 预减后丢弃（用户可见 FAIL）；其他异常 → `RECONSUME_LATER` 重投，重试耗尽进 `%DLQ%seckill-order-consumer`。
> - 验证脚本为 `scripts/phase2-verify.ps1`；broker 事务参数 `transactionTimeOut=6000`、`transactionCheckInterval=10000`、`transactionCheckMax=15`。
> - 事务 commit/rollback 计数暂未单独 Micrometer 埋点，通过应用日志与验证脚本核对，P6 前补齐。

**目标**：用事务消息替换秒杀 RabbitMQ 异步下单链路，修补「Redis 已扣、消息未发」窗口；延迟关单继续走 RabbitMQ。

**改动清单**
- `pom.xml`：`org.apache.rocketmq:rocketmq-client:5.3.1`（手写 Producer/Consumer Bean，避免 Spring Boot Starter 版本耦合）。
- 新增 `config/RocketMqConfig.java`：
  - `TransactionMQProducer`（`transactionListener`、`namesrvAddr`、`sendMsgTimeout`）
  - `DefaultMQPushConsumer`（`seckill-order-consumer`、`consumeThreadMin/Max`、`maxReconsumeTimes=3`）
- 新增 `mq/rocketmq/`：
  - `SeckillOrderTransactionProducer.java`
  - `SeckillOrderTransactionListener.java`（`executeLocalTransaction` / `checkLocalTransaction`）
  - `SeckillOrderRocketConsumer.java`
  - `RocketMqConstants.java`
- 新增 `service/SeckillLocalTransactionService.java`：抽出「Lua 预减 + 一人一单」本地事务逻辑。
- `SeckillServiceImpl.execute` 重构：
  1. 路径/本地售罄/时间窗校验（不变）
  2. 发送半消息（携带 userId、seckillSkuId、收货信息、messageId）
  3. 本地事务执行 Lua：
     - 返回 1 → `COMMIT_MESSAGE`
     - 返回 0/-1 → `ROLLBACK_MESSAGE`（并置本地售罄标记）
  4. 接口返回 QUEUING
- `checkLocalTransaction`：
  - Redis 已购集合包含 userId → COMMIT
  - 秒杀 key 不存在或库存未扣 → ROLLBACK
  - 无法判定 → UNKNOW（由 broker 继续回查）
- 消费端复用 `handleSeckillOrder`，`mq_consume_log` 幂等键改为 `rocketmq:seckill-order`。
- `RabbitConfig` / `MqConstants`：只保留延迟关单与关单队列；删除秒杀下单交换机/队列/DLX（或标记 `@Deprecated` 后删除）。
- `docker-compose.yml`：`rocketmq-namesrv`、`rocketmq-broker`（`broker.conf`：`brokerIP1=rocketmq-broker`、`autoCreateTopicEnable=true`、`transactionCheckInterval=6000`）。
- `scripts/phase2-verify.ps1`：验证成功/售罄/重复/回查/重复消费五类场景。

**关键设计**
- 事务消息的「本地事务」= Redis Lua 预减；这是现有架构里真正的本地事务边界。
- 消费端仍做 DB 条件扣减 + 唯一索引 + 幂等表，事务消息不替代最终防线。
- 消费失败 `RECONSUME_LATER`，3 次后进 `%DLQ%seckill-order-consumer`；增加 DLQ 监控指标与告警日志。
- 半消息发送失败：execute 直接返回系统繁忙，不扣 Redis（因为本地事务未执行）。

**验收**
- 成功：Redis 库存 -1、订单落库、`mq_consume_log` 一条、结果轮询 SUCCESS。
- 售罄/重复：无消息被消费、Redis 库存不变、结果 FAIL/REPEATED。
- broker 重启/半消息悬挂：事务回查后状态收敛，不产生重复订单。
- 重复投递：消费幂等拦截，订单数不增加。
- 指标：`rocketmq_tx_commit_total` / `rollback_total` / `check_total` 可查。

**风险/回退**
- RocketMQ 容器内存约 1GB：broker JVM 限 `-Xms512m -Xmx512m`。
- 事务回查间隔默认 6s，演示可调 3s；生产保持默认。
- 如事务消息异常，可通过 `mall.mq.seckill.type=rabbit` 开关回退旧链路（保留一版代码）。

### P3 ShardingSphere 订单域分库分表 ✅ 已完成

> 实施记录（与下方设计的差异）：
> - 订单库为**两个独立 MySQL 容器** `mall-mysql-order0/1`（库 `mall_order_0/1`，端口 13307/13308），不是同一实例内的两个 schema。
> - 分片算法：库 `ds${user_id % 2 + 1}`，表 `${(user_id >> 1) % 4}`。原设计「库 `user_id%2` + 表 `user_id%4`」会让表后缀隐含奇偶位，导致 8 分片中 4 个永远为空；改为库取最低位、表取次低 2 位后 8 分片均可落数据。
> - 分片表主键改为雪花 ID（`IdType.ASSIGN_ID`），不使用 `AUTO_INCREMENT`，避免跨分片主键重复。
> - 引入 **XA 分布式事务（Atomikos）**：`@Transactional` 内会同时写订单库（ds1/ds2）与主库（`pms_sku` 库存、`sms_seckill_sku`、`mq_consume_log`），必须保证原子性。
> - 表结构脚本合并为 `sql/sharding/order-shard-schema.sql`（12 张表，无 `USE`，依赖容器 `MYSQL_DATABASE`）。
> - 验证脚本为 `scripts/phase3-verify.ps1`（状态流转、单分片路由、广播、分片均衡）；`scripts/phase2-verify.ps1` 已适配分片库计数。

**目标**：订单域 2 库 × 4 表，`user_id` 分片；买家查询单库路由，管理端跨库广播可接受。

**改动清单**
- `pom.xml`：`org.apache.shardingsphere:shardingsphere-jdbc:5.5.0`。
- 新增 `src/main/resources/sharding.yaml`：
  - `dataSources`: `ds0`（mall_seckill）、`ds1`（mall_order_0）、`ds2`（mall_order_1），HikariCP。
  - `rules`：
    - `!SHARDING`：`oms_order` / `oms_order_item` / `sms_seckill_order`，`actualDataNodes: ds${1..2}.<table>_${0..3}`，`databaseStrategy` + `tableStrategy` 均用 `user_id` 的 inline 算法。
    - `!SINGLE`：非分片表（用户/商品/分类/秒杀配置/`mq_consume_log`）默认落 `ds0`。
  - `props`: `sql-show=false`（压测）/ `true`（排查）。
- `application-prod.yml`：
  - `spring.datasource.driver-class-name: org.apache.shardingsphere.driver.ShardingSphereDriver`
  - `spring.datasource.url: jdbc:shardingsphere:classpath:sharding.yaml`
  - 移除生产 Druid 配置（ShardingSphere 内部 Hikari）。
- `sql/sharding/`：
  - `01-create-databases.sql`：创建 `mall_order_0`、`mall_order_1`。
  - `02-order-shard-schema.sql`：每库 `oms_order_0..3`、`oms_order_item_0..3`、`sms_seckill_order_0..3`。
  - `03-migrate-existing.sql`：存量订单按 `user_id` 迁移（开发环境为空，保留脚本）。
- `docker-compose.yml`：新增 `mysql-order-0`、`mysql-order-1`（13307/13308，`innodb-buffer-pool-size=128M`）。
- Mapper/Service 改造（必须带 `user_id`，避免全库广播）：
  - `OmsOrderMapper`：`payIfPending(id,userId)`、`cancelIfPending(id,userId,reason)`、`shipIfPaid(id,userId)`、`completeIfShipped(id,userId)`。
  - `OrderDelayMessage` 增加 `userId`；`OrderServiceImpl.closeExpiredOrder(orderId,userId,messageId)`。
  - `OmsOrderItem` 查询统一加 `user_id`（`doPage` 批量查明细、`toDetailVO`、`restoreStockByOrder`）。
  - `SmsSeckillOrder` 查询/删除加 `user_id`；`SeckillService.restoreAfterOrderCancel(orderId,userId)`。
  - `OrderPageQuery` 增加可选 `userId`（管理端按用户路由；不传则广播）。
- `MybatisPlusConfig`：保留分页插件，验证与 ShardingSphere 的 LIMIT/COUNT 重写兼容。

**关键设计**
- 三张订单表使用同一 `user_id` 分片算法 → 同一用户的订单主表、明细、秒杀关联落在同一物理库，`@Transactional` 仍是本地事务，不引入分布式事务。
- 雪花 ID 保证全局唯一；`order_sn` 唯一索引在每个分片内有效（全局唯一由 ID 生成保证）。
- 管理端按 `order_sn`/`id` 查询或状态更新会广播到 8 个分片，低流量可接受；文档明确标注。
- 分页：ShardingSphere 负责 LIMIT 重写与结果归并；MyBatis-Plus 只负责生成逻辑 SQL。

**验收**
- 插入 10,000 条订单，8 个分片分布偏差 <10%。
- 买家「我的订单」SQL 只命中 1 个物理分片（开 `sql-show` 验证）。

### P5 2k+ QPS 压测与瓶颈分析 ✅ 已完成

**目标**：售罄拒绝路径 ≥2000 QPS，成功路径 ≥1000 QPS；给出瓶颈定位与优化前后对比。

**代码优化（按收益排序）**
1. **合并 Redis 往返**：把动态路径校验并入 Lua。
   - 现链路：`GET path` + `GET sessionId` + `HGET skuCache` + `Lua` = 4 次 RTT。
   - 优化后：`Lua` 内校验 path + 一人一单 + 库存 = 1 次 RTT。
   - 返回码：`-2` 路径无效 / `-1` 重复 / `0` 售罄 / `1` 成功。
2. **本地秒杀商品缓存**：`Caffeine<Long, SeckillSkuCache>`，TTL 10s；`uploadToRedis` 后通过 Redisson `RTopic` 广播失效（多实例一致）。
   - 省掉 `GET sessionId` + `HGET skuCache` 两次 RTT。
3. **保留本地售罄标记**（已有，1026 vs 476 的 2.16× 证据）。
4. **连接池/线程**：Lettuce `max-active=64`、`min-idle=16`；Tomcat `max-threads=400`、`accept-count=1000`、`max-connections=10000`。
5. **压测 profile**：`TRACING_SAMPLING_PROBABILITY=0`、关闭 SQL 打印、Sentinel 阈值调高/关闭（仅压测）。
6. **4 实例**：Nginx upstream app1..app4，单实例 `-Xmx384m`。

**压测矩阵**

| 场景 | 实例 | 代码 | 目的 |
|---|---|---|---|
| A 售罄拒绝 | 2 | 优化前 | 复现基线 1026 |
| B 售罄拒绝 | 4 | 优化前 | 验证水平扩展线性度 |
| C 售罄拒绝 | 4 | 优化后（1 RTT） | 目标 ≥2000 |
| D 成功下单 | 4 | 优化后 | 目标 ≥1000，消费不堆积 |
| E 混合 90/10 | 4 | 优化后 | 5 分钟持续，验证稳定性 |

**指标采集**
- 应用：`mall_seckill_execute_total{result}`、`mall_seckill_execute_duration_seconds`、JVM CPU/GC（Micrometer）。
- Redis：`INFO commandstats`（`evalsha` 占比）、`INFO stats`（ops/s）、`SLOWLOG`。
- MySQL：`SHOW GLOBAL STATUS`（QPS/TPS/Innodb_row_lock_waits）、慢查询日志。
- RocketMQ：`mqadmin consumerProgress`、`%DLQ%` 数量、发送 RT。
- 链路：Zipkin 采样少量请求定位耗时分布；JFR（`-XX:StartFlightRecording`）抓 CPU 热点。

**瓶颈分析方法**
1. 先看 QPS-并发曲线：是否过早平台化（说明单点瓶颈）。
2. 对比 Redis RTT 次数与 `evalsha` QPS：确认是否 Redis 网络往返。
3. 应用 CPU 是否打满：打满则看 JFR 热点（序列化/JSON/日志）。
4. 成功路径看 MySQL 行锁等待与 MQ 发送 RT；消费看队列堆积。
5. 每项优化单独做 A/B，避免多个变量混在一起。

**验收**
- C 场景 ≥2000 QPS，错误率 <0.1%，p99 <150ms。
- D 场景 ≥1000 QPS，队列无持续堆积，消费 TPS ≥ 生产速率。
- 对账：Redis 预减总量 = DB 订单数 + 失败补偿数；无超卖、无重复订单。
- `benchmark-report-v2.md` 含：环境、方法、矩阵、瓶颈表、优化前后对比、复现命令。

**实施记录（与设计的差异）**

已落地（详见 `benchmark-report-v2.md` 第 7 节）：

| 设计项 | 实际实现 | 说明 |
|---|---|---|
| 动态路径校验并入 Lua | **未合并**，保留独立 `GET` | 路径失效语义更清晰，拒绝路径仍只剩 1 次 RTT（本地标记命中时 0 次） |
| 本地秒杀商品缓存 + Redisson 广播失效 | Caffeine TTL 5s（`mall.seckill.sku-local-cache-seconds`） | 用 TTL 代替广播，省掉一个广播通道；商品信息最长滞后 5s |
| 本地售罄标记 | 前移到 `execute` 第 1 步，新增 TTL 10s（`SECKILL_LOCAL_MARK_TTL_SECONDS`） | 多实例补货后靠 TTL 自愈，解决「只有处理预热请求的实例清标记」导致的误拒绝 |
| 合并 Lua 内的结果 key 删除 | 已实现（`KEYS[3]`） | 预减成功顺带 `DEL` 结果 key |
| 4 实例扩容 | **回退为 2 实例** | 4 实例 reject c=200 只有 1081 QPS（2 实例 2222），首轮 601 个 5s 超时，宿主内存不足 |
| 额外优化 | 用户/权限 Caffeine 30s、热路径 INFO→debug、Nginx `access_log off` + 4 worker + keepalive 128 | 认证缓存与日志降级是压测中定位到的隐性开销 |

实测结果：

| 场景 | 结果 |
|---|---|
| 售罄拒绝（2 实例经 Nginx，8000 请求/轮） | c=100 **2539**、c=200 **2222**、c=300 1063~1376、c=400 1128~1334 QPS，错误 0 |
| 成功下单（一人一单，3000 用户） | c=200 峰值 **1013** QPS、中位 847；c=100 p99 142ms；c=400 792 QPS |
| 数据一致性 | 8 分片累计 27005 笔秒杀订单，按 `user_id` 重复 0；超时关单回补库存全链路验证通过 |
| 错误率 | 6 万+ 请求中 3 个客户端 5s 超时（<0.01%） |

**瓶颈结论**

1. 拒绝路径业务侧已无 Redis 往返，瓶颈转移到 Nginx（Docker Desktop 单 VM）与压测客户端；同一配置跨轮次波动 1063~2539，宿主空闲内存仅约 0.4~0.7GB 是主因。
2. 成功路径受 **CPU** 限制：压测时 app1/app2 各 300~360% CPU（合计约 6.5/8 核），因为同一 JVM 既发 RocketMQ 事务消息又消费，消费端 Atomikos XA 两阶段提交要写 3 个 MySQL。要继续提升需拆分消费进程或降低 XA 参与方（超出本阶段范围）。
3. p99 < 150ms 与 ≥1000 QPS 在本机不可兼得：c≤100 时 p99 可达 118~142ms，c≥200 时 CPU 打满产生 400~700ms 排队。

**风险/回退**
- 本地机器 8C/16T、12GB：4 实例 + 全中间件内存紧张；用 compose `mem_limit` 限制，必要时降到 3 实例并记录。
- 压测噪声：固定 CPU 频率/关闭其他项目容器（需用户确认），每组至少 2 轮取平均。
- 2k 未达标：优先确认是否 Redis 单线程/网络瓶颈，再考虑 pipeline、读写分离或增加 Redis 实例（不在本方案默认范围）。
