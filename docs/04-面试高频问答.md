# 文档四：面试高频问答（含标准答案）

> 用法：先自己答，再对照答案。标 ⭐ 的是极高频必背。答案长度按"面试口述 1-3 分钟"设计。
> 详解类追问见文档一/二/三，本文档给"考场标准答法"。

## 一、项目整体与开场

### Q1 ⭐ 先简单介绍一下这个项目

> 这是我独立设计开发的高并发电商秒杀系统 mall-seckill，前后端分离。业务上包含 RBAC 权限、商品中心、购物车、订单、秒杀、搜索，形成完整交易闭环。技术上基于 Spring Boot 3 + Java 17，用 Redis Lua 原子预减库存、本地内存售罄标记构建高并发秒杀漏斗，RocketMQ 事务消息异步下单，ShardingSphere 订单域 8 分片，Elasticsearch + IK 商品搜索，Nacos/Sentinel 做服务治理，并配套 Caffeine+Redis 多级缓存、JWT 安全认证、Prometheus/Grafana 监控、Zipkin 链路追踪和 Docker Compose 一键部署。我还做了真实压测：售罄拒绝路径 P0 基线 787 QPS，升级后峰值 2539 QPS（c=100）/ 2222（c=200）；成功下单峰值 1013、中位 847 QPS，8 分片累计 27005 单、按用户重复 0。

**要点**：30 秒内讲清"做了什么 + 核心技术 + 量化结果"。

### Q2 ⭐ 为什么做这个项目

> 我想系统地实践高并发场景的工程解法。秒杀是非常典型的"读多写多、瞬时流量远超库存"的场景，能把缓存、分布式锁、消息队列、幂等、分布式一致性这些后端核心技术串成一条真实链路来用，而不是停留在单点 demo。

### Q3 ⭐ 这个项目最大的难点是什么

> 难点是怎么在"不能用强一致分布式事务拖垮性能"的前提下保证不超卖。我的解法是分层：Redis 侧用 Lua 脚本原子完成判重和预减；DB 侧用条件扣减作为最终防线；消费失败有补偿和死信队列；本质是用最终一致性和纵深防御换吞吐。另一个难点是压测和优化，通过本地售罄标记把售罄流量的 Redis 调用完全省掉，实测拿到 2.16 倍提升。

### Q4 这个项目有多少代码？你写了多久

（按真实情况回答）后端 159 个主代码 Java 类 + 10 个测试类（另有 1 个测试辅助类），9 个初始化 SQL 脚本，前端 4 个核心页面；测试 71 个用例。强调从设计、编码、测试、压测到部署文档全部独立完成。

### Q5 项目中你最有成就感的部分

> 本地售罄标记的优化。它逻辑不复杂，但通过压测对比拿到了明确的 2.16 倍数据，并且能观察到系统瓶颈从 Redis 转移到应用 CPU——这种"假设被数据验证"的过程让我理解了性能优化要靠测量而不是猜。

### Q6 你觉得项目还有什么不足

> 有，而且我知道怎么改。一是回退链路（`mall.rocketmq.enabled=false`）仍是 afterCommit 发 RabbitMQ，存在「DB 已提交、消息未发、进程宕机」的极小丢消息窗口，生产应加本地消息表（Outbox）和定时对账；默认的 RocketMQ 事务消息链路已通过半消息 + 回查消除该窗口，但两条链路并存需要在面试中说清。二是本地缓存失效没有跨实例广播，多实例间靠短 TTL 收敛，可以用 Redis Pub/Sub；三是 Zipkin 默认内存存储，生产应接 Elasticsearch。能主动说出不足和修法，比声称完美更可信。

## 二、架构设计

### Q7 ⭐ 为什么秒杀不能直接操作数据库

> 秒杀流量是库存的几百倍，直接打 DB 会有两个问题：大量并发去更新同一行库存产生严重行锁竞争，连接池被打满；而且 99% 的请求最终是失败的，让它们消耗数据库资源毫无意义。所以要用漏斗把无效请求在到达 DB 前逐层拦截。

### Q8 ⭐ 讲一下秒杀的整体架构 / 流量漏斗

> 六级漏斗，原则是成本递增：① 图形验证码、用户绑定动态路径、限流挡住机器和连点；② 本地内存售罄标记，零网络 IO 拒绝；③ 商品缓存校验 + Redis Lua 原子判重预减；④ 预减成功发 MQ，接口返回排队中；⑤ 消费端 Redisson 锁串行 + DB 条件扣减最终防超卖 + 订单落库；⑥ 事务提交后写结果 key，前端轮询 QUEUING/SUCCESS/FAIL。

### Q9 为什么用 Nginx，它做了什么

> Nginx 是唯一入口，做四件事：托管前端静态资源；把 /api 和 /doc.html 反向代理到后端双实例并做轮询负载均衡；SPA 路由 try_files 回退 index.html；keepalive 长连接减少握手。后端无状态，水平扩展只需加实例并更新 upstream。

### Q10 为什么后端部署两个实例

> 验证水平扩展和负载均衡，也避免单点。实例无状态，会话和库存全部外置 Redis/DB；实例各自持有 Caffeine 和售罄标记，这些是允许最终收敛的本地优化。

### Q11 如果秒杀流量再大 10 倍怎么扩展

> 分层回答：接入层 Nginx 扩容/用 LVS；应用层无状态直接加实例，拒绝路径 QPS 与实例数近似线性；Redis 可做分片集群（库存 key 按商品 hash 分散），热点 key 还可用本地缓存/多副本读；消费层加消费者实例、MySQL 订单表按用户 ID 分库分表、批量插入；MQ 保证消费速率 ≥ 生产速率。核心是让每一层都能独立水平扩展。

### Q12 为什么不用 Spring Cloud 微服务/网关

> 项目现在已引入 Nacos 注册/配置与 Sentinel 做轻量治理，但并没有拆微服务、也没有上网关：单体模块化 + Nginx 已满足路由与负载均衡，拆分会把本地事务变成分布式事务，增加与核心目标无关的复杂度。如果继续演进，网关可以用 Spring Cloud Gateway 承担路由和限流，服务按商品/订单/秒杀拆分。选型要匹配阶段。

### Q13 你的分层是怎么划分的

> controller 只做参数接收和结果返回；service 承载业务逻辑和事务；mapper 访问 DB；DTO 入参、VO 出参、entity 对表严格分离；与业务无关的能力放 common；后台接口独立到 admin 包。

## 三、Redis 与 Lua

### Q14 ⭐ Redis 怎么解决超卖

> 三层：Redis Lua 脚本把"一人一单判重 + 库存预减"作为原子操作执行，Redis 侧不可能扣成负数；消费端 DB 再做条件更新 `UPDATE ... WHERE seckill_stock>=1`，即使 Redis 数据异常 DB 也不会超卖；消费失败会补偿归还。真正的最终防线是数据库条件扣减。

### Q15 ⭐ 为什么要用 Lua，原子性怎么来的

> Redis 命令执行是单线程的，一段 Lua 会被当作不可分割的整体执行，中间不会插入其他客户端命令，所以多步操作天然原子；同时多步合并成一次调用还减少网络往返。原子性来自 Redis 单线程模型，不是 Lua 本身。

### Q16 ⭐ 手写并讲解预减 Lua（现场写）

> （答案见文档二 2.2）先 SISMEMBER 判重返回 -1；GET 库存，nil 或不足返回 0；DECRBY + SADD 后返回 1。注意先判重（重复流量最大）、nil 按售罄 fail-safe、tonumber 显式转换。

### Q17 为什么不用 DECR，扣成负数再回补

> DECR 是先扣后判，存在"已经负了"的并发窗口，回补逻辑复杂。先判断够不够再扣，从逻辑上保证不会出现负库存，更安全。

### Q18 ⭐ 一人一单怎么实现

> 三个层次：Redis Set（seckill:ordered:{skuId}）在 Lua 里 SISMEMBER + SADD 快速判重；消费时查 sms_seckill_order 是否已有该用户+商品记录；DB 上有 uk_user_sku 唯一索引最终兜底。

### Q19 ⭐ 本地售罄标记是什么，为什么快

> 一个 ConcurrentHashMap，Lua 返回售罄后置位，execute 最前面检查，命中就在 JVM 内存直接拒绝，零网络 IO。秒杀抢空后仍有大量流量涌入，这批流量成本被降到最低。P0 前基线压测 476→1026（2.16 倍）；P5 前移标记并加 10s TTL 后，拒绝路径峰值 2539 QPS。

### Q20 ⭐ 多实例下本地标记不一致怎么办

> 不影响正确性只影响效率：每个实例最多走一次 Redis 拿到售罄结果就会自己置位收敛。库存回补时其他实例可能短暂误拒，是可接受的可用性窗口；项目已给标记加 10s TTL（`mall.seckill.local-mark-ttl-seconds`），补货后各实例最迟 10s 自愈，要更强可用 Redis Pub/Sub 广播清标记。

### Q21 缓存穿透是什么，你怎么解决

> 请求数据库中不存在的数据，缓存永不命中，恶意攻击可打挂 DB。项目用空值缓存：查不到就缓存空占位符且短 TTL，本地 Caffeine 也缓存空值。没用布隆过滤器是因为数据规模小、空值方案更简单。

### Q22 缓存击穿怎么解决

> 热点 key 过期瞬间大量请求同时回源。用 Redisson 互斥锁只放一个线程重建，其他线程等待后读缓存；拿到锁还要 DCL 二次检查，防止等锁期间已被重建。

### Q23 缓存雪崩怎么解决

> 大量 key 同时过期或 Redis 宕机。TTL 加随机抖动打散过期时间；高可用集群、本地缓存兜底、接口限流保护 DB。

### Q24 ⭐ Redis 和 MySQL 一致性怎么保证

> 采用 Cache Aside：读穿缓存，写时先更新库再删缓存，删除幂等、下次读重建。极端并发下先更库再删缓存的不一致窗口极小，且有 TTL 兜底。多级缓存失效先删 Redis 再删 Caffeine；多实例 L1 靠短 TTL（300s，短于 L2）收敛。强一致会牺牲性能，这里按业务接受最终一致。

### Q25 为什么是删缓存不是更新缓存

> 避免无效更新冷数据；写并发下更新可能写乱顺序；删除幂等，读时按最新库重建更可靠。

### Q26 ⭐ 讲一下 Redisson 看门狗

> 显式传 leaseTime 时到点自动释放、看门狗不生效；不传时默认 30s 租约，后台线程每 10s 检查客户端存活并续期，防止业务没执行完锁就过期。我项目显式指定租约，因为只保护很短的 DB 操作，也避免客户端宕机后锁被无限续期。

### Q27 Redis 分布式锁怎么演进的

> SETNX/EXPIRE 非原子会死锁 → SET NX EX 原子加锁 → value 存唯一标识 + Lua 比对解锁防误删 → 看门狗续期防业务超时 → 主从切换丢锁用 RedLock（有争议）。项目的正确性最终靠 DB 条件扣减和唯一索引兜底，不单纯依赖锁。

### Q28 RedLock 了解吗，有什么争议

> 向多个独立 Redis 节点申请锁，多数成功才算拿到，防单节点切换丢锁。Martin Kleppmann 质疑它依赖时钟（时钟跳变会破坏安全性）且无法像 fencing token 那样防止客户端暂停后误写。更稳的是 etcd/ZooKeeper 共识锁，或锁降并发 + DB 约束兜底。

### Q29 Redis 为什么快 / 单线程模型

> 纯内存；IO 多路复用单线程处理大量连接；无线程切换和锁。Redis 6 后网络读写有多线程，但命令执行仍单线程。

### Q30 秒杀 key 丢了（Redis 宕机重启）怎么办

> 库存以 DB seckill_stock 为准，Redis 是加速层；可以重新执行预热恢复计数和缓存；Lua 里 stock==nil 会按售罄 fail-safe，不会因为读不到库存就放行。

### Q31 项目用了哪些 Redis 数据结构、为什么

> 库存/令牌/路径用 String（计数、单值）；一人一单用 Set（成员判断 O(1)）；购物车和场次商品用 Hash（按 field 独立读写）；限流用 ZSet（按 score 时间范围统计）。结构选择服务于操作特征。

## 四、消息队列与一致性

> 本节以 RabbitMQ 回退链路讲解消息可靠性；默认链路是 RocketMQ 事务消息，专项问答见 [07-交易中台面试问答](07-交易中台面试问答.md)。

### Q32 ⭐ 为什么秒杀要用消息队列

> 削峰、异步：同步接口只做 Redis 预减和发消息就返回排队中，把瞬时洪峰摊平成消费者匀速处理，保护 MySQL；同时解耦，落单逻辑独立演进和重试。

### Q33 ⭐ MQ 消息怎么保证不丢

> 默认链路已改为 RocketMQ 事务消息：半消息 + 本地事务（Lua 预减）+ Broker 回查，售罄/重复直接回滚。RabbitMQ 回退链路的三段保障是：生产端 publisher confirm + returns（mandatory）感知投递和路由失败；Broker 端交换机、队列、消息全部持久化；消费端手动 ACK，业务成功才确认。

### Q34 ⭐ 消息重复消费怎么解决

> 承认重复投递是常态（ACK 网络丢失），用消费幂等：mq_consume_log 表 messageId 唯一索引 + INSERT IGNORE，只有首次插入成功才执行业务。业务层还有 sms_seckill_order 查询和 DB 唯一索引多层兜底。

### Q35 ⭐ 幂等日志和业务为什么必须同一事务

> 业务成功提交，日志留存拦截后续重投；业务失败回滚，日志一起回滚，消息重投时可以重新执行。如果日志提前提交，业务失败后重投会被误判已消费，消息就再也处理不了。

### Q36 为什么用 INSERT IGNORE，不先查后插

> 先查后插有并发窗口，两条相同消息可能都查到不存在。INSERT IGNORE 由唯一索引保证只有一个插入成功，原子且简单。

### Q37 ⭐ 消费失败的完整处理流程

> SeckillOrderListener 捕获异常：先补偿（确认未落单后 Redis 库存 +1、SREM 已购标记、写 FAIL、清售罄标记，让用户可重试）；再 basicNack(requeue=false)，消息经 DLX 进死信队列；死信监听器记录 x-death 原因告警并 ACK，避免毒消息循环。

### Q38 为什么 nack 要 requeue=false

> requeue=true 对毒消息会形成"投递-失败-重回"无限循环打满 CPU。requeue=false 把问题消息隔离到 DLQ，主链路保持畅通。

### Q39 ⭐ 死信队列在项目里有几个用途

> 两个：订单超时关单是刻意让消息活到 TTL 过期成为死信，把 DLX 当延迟队列；秒杀消费失败是异常兜底，拒绝消息进 DLQ。同一机制两个目的。

### Q40 消息变死信的原因有哪些

> 消费者 reject/nack 且 requeue=false；消息 TTL 过期；队列达到最大长度。死信带 x-death 头记录原因和原队列等信息。

### Q41 为什么不用延迟插件

> TTL+DLX 是原生能力无需装插件，部署简单；订单超时统一用队列级 TTL 最合适。要知道队列级 TTL 有队头阻塞特性，每单超时不同时更明显——本项目 TTL 一致不受影响。

### Q42 ⭐ 为什么不用 Seata/2PC

> 2PC/Seata AT 同步阻塞、锁持有时间长，秒杀高并发下吞吐不可接受，且对 Redis 这类非 JDBC 资源支持不直接。秒杀业务允许短暂不一致和个别失败，追求高吞吐下的最终一致，所以用"Lua + 本地事务 + 失败补偿 + 死信兜底"替代。

### Q43 ⭐ Lua 成功但发 MQ 前宕机会怎样

> 默认的 RocketMQ 事务消息链路不存在这个窗口：先发半消息，再在本地事务里执行 Lua 预减并把结果写入 Redis 标记，Broker 未收到确认时回查标记决定提交或回滚。只有回退到 RabbitMQ afterCommit 链路时，才有「Lua 成功、DB 未提交/进程宕机、消息未发出」的窗口；生产修法是 Outbox 本地消息表 + Redis 已购集合与 DB 订单定时对账，个人演示环境靠概率和轮询兜底。

### Q44 讲一下本地消息表（Outbox）

> 与业务同一个 DB 事务把待发消息写入本地消息表；独立任务扫描待发送记录发 MQ，收到 confirm 再标记已发送，失败无限重试；消息带 messageId，消费端幂等让重试安全。它把跨系统一致性转成同库事务 + 可靠重试。

### Q45 消费成功但 ACK 丢了怎么办

> Broker 重投，mq_consume_log 唯一索引拦截，幂等跳过，不会重复落单。

### Q46 订单超时消息和支付同时发生

> 关单用条件更新只有待支付才能改，支付也是条件更新，二者 CAS 竞争：支付成功则关单影响行数 0 直接跳过，不会误关已支付订单。

### Q47 prefetch 是什么

> 消费者最多同时持有多少未确认消息，防止慢消费者被压垮，也让消息在多消费者间按能力分配。项目设 10。

### Q48 消息积压怎么排查处理

> 先看是生产突增还是消费变慢（下游 DB/接口）；临时扩消费者、批量消费；根本上保证速率匹配——P5 压测成功路径峰值 1013 QPS，消费端未出现队列堆积（详见 benchmark-report-v2.md 第 7 节）。

## 五、订单与购物车

### Q49 ⭐ 普通下单的完整流程

> 八步（见文档一 3.4）：幂等令牌 Lua 一次性消费 → 取服务端购物车勾选项 → 批量校验商品在售和库存并算总价 → 条件 SQL 扣库存，0 行就回滚 → 落订单主表（雪花号、待支付）→ 落明细（全部快照）→ 清购物车（事务内）→ afterCommit 才发延迟关单消息。

### Q50 ⭐ 订单为什么要做快照，哪些字段

> 商品后来会改名、改价、下架，订单要忠实反映下单时的状态用于展示和对账。明细冗余商品名、规格文本、单价、图片、SKU/SPU ID；秒杀单价格是秒杀价快照。

### Q51 为什么下单只信服务端购物车

> 前端传的商品、数量、价格都可能被篡改（改价是最典型的攻击）。服务端从 Redis 购物车取勾选项、从 DB 取价格，前端数据仅用于收货信息。

### Q52 怎么防止重复下单

> 进入结算页发幂等令牌，下单时 Lua 原子 GET+DEL，只有一个请求能消费成功；订单号雪花生成，DB 唯一索引最终兜底。

### Q53 ⭐ 订单状态机怎么设计、怎么防并发错乱

> 待支付→已支付/已取消→已发货→已完成等，每个流转都用条件更新 `UPDATE ... WHERE id=? AND status=前置状态`（CAS），影响行数 0 就说明状态已变并给出对应提示，天然防并发。

### Q54 超时关单怎么实现

> 下单事务提交后发消息到 TTL 延迟队列，过期经 DLX 到关单队列；消费者 CAS 关单（仍待支付才生效）并回补库存。天然幂等，重复投递安全。

### Q55 订单取消后库存怎么回补

> 按 order_type 分流：秒杀单调 seckillService.restoreAfterOrderCancel，回补 DB 秒杀库存、删秒杀订单关系（否则无法复购）、Redis 库存 +1、SREM 已购集合、清售罄标记；普通订单回补 pms_sku。

### Q56 购物车怎么存的

> Redis Hash：key=cart:user:{userId}，field=skuId，value 购物项 JSON；支持数量、单选、全选；价格实时来自 DB，购物车只存状态。

## 六、认证授权与安全

### Q57 ⭐ 讲一下 JWT 认证流程

> 登录校验密码后签发 access/refresh 双 token；access 放内存、每次请求 Authorization 头，过滤器验签、验类型、查黑名单后构造认证上下文；refresh 存 httpOnly Cookie，仅用于换新。无状态、服务端不存会话。

### Q58 ⭐ 为什么用双 token 且分开存储

> access 短期即使泄露风险窗口小；refresh 长期但存 httpOnly Cookie 使 JS 读不到（防 XSS），SameSite=Lax 使跨站请求不带（缓解 CSRF）。分工把"方便访问"和"长期凭证安全"分开。

### Q59 refresh token 被盗怎么办

> refresh 接口做轮换：用一次旧 refresh 换新并把旧的拉黑，攻击者拿到的旧 token 失效；检测到黑名单 refresh 被使用还可视为盗窃，强制该用户所有会话下线。

### Q60 ⭐ 主动登出怎么实现

> 把当前 access token 的 MD5 写 Redis 黑名单，TTL 等于其剩余有效期，过滤器拦截；过期后黑名单自动清理不膨胀；同时清除 refresh Cookie。

### Q61 RBAC 模型是什么

> 用户-角色-菜单三张实体加两张关联表。登录加载角色为 GrantedAuthority，方法级 @PreAuthorize 控制接口；/auth/info 返回权限和菜单供前端渲染。

### Q62 密码怎么存储

> BCrypt，自带随机盐（hash 内含盐和强度因子），不可逆；登录用 matches 比对。登录失败统一提示"用户名或密码错误"，不暴露用户是否存在。

### Q63 项目里禁用了 CSRF，为什么

> JWT 认证本身是无状态的、靠 Authorization 头而不是 Cookie 自动带凭证，传统 CSRF 攻击前提不成立；但 refresh 走 Cookie，所以用 SameSite=Lax 专门防护。两者针对的凭证不同。

### Q64 httpOnly / SameSite / Secure 各是什么

> httpOnly 禁止 JS 读取防 XSS 窃取；SameSite 控制跨站是否携带（Lax 只允许顶级导航 GET，跨站 POST 不带）防 CSRF；Secure 限定 HTTPS 才发送，生产开启（项目通过配置切换）。

## 七、限流与防护

### Q65 ⭐ 你的限流怎么实现

> 自定义 @AccessLimit（窗口秒数、最大次数、用户/IP 维度）+ AOP 切面，Redis ZSet 滑动窗口：Lua 先清窗口外成员、ZCARD 判阈值、再写入。滑动窗口没有固定窗口的临界突刺，超限返回 429。

### Q66 滑动窗口 vs 固定窗口

> 固定窗口在边界可能连续放行两个满窗口（瞬间 2 倍流量）；滑动窗口按真实时间统计更平滑。代价是 ZSet 要存每个请求（用 UUID 成员 + pexpire 清理）。

### Q67 限流维度为什么要分用户和 IP

> 已登录按用户精准限流防连点；未登录场景按 IP 兜底防匿名刷。IP 通过 RequestUtils 解析 X-Forwarded-For 等头拿真实 IP（在 Nginx 后面）。

### Q68 验证码防的是什么

> 机器批量请求和接口自动化。算术图形增加识别成本；答案存 Redis 短 TTL，校验 Lua 读+删原子、一次性消费，答错也删，防止枚举答案。

### Q69 动态路径解决什么

> 真实下单地址开抢且过验证码后才下发，路径按用户+商品+盐 MD5、短 TTL，execute 按用户绑定 key 比对。防止脚本提前知道固定接口刷单和跨用户盗用。

## 八、监控、部署与测试

### Q70 ⭐ 项目怎么做监控

> Micrometer 定义秒杀出口计数、分结果耗时直方图（P95/P99）、消费结果计数，/actuator/prometheus 暴露，Prometheus 定时抓取，Grafana 做秒杀概览看板。业务指标能和压测数字交叉验证。

### Q71 链路追踪怎么做的

> Micrometer Tracing + Brave + Zipkin，W3C traceparent 传播，HTTP/Redis/MQ 自动透传，响应头 X-Trace-Id 返回；采样率可配。日志 pattern 带 traceId 可串联多实例。

### Q72 为什么需要链路追踪

> 一个秒杀请求跨越应用、Redis、MQ、消费者、DB，出问题时微服务/异步场景下日志无法关联。traceId 把整条链路的 span 和耗时串起来，快速定位瓶颈和错误节点。

### Q73 Docker Compose 里有哪些服务

> 主库 MySQL（自动执行 9 个初始化 SQL）、2 个订单分库 MySQL、Redis、RabbitMQ（延迟关单）、RocketMQ（事务消息）、Nacos、Sentinel、Elasticsearch、Zipkin、后端双实例、Nginx、Prometheus、Grafana。项目名固定 mall-seckill，docker compose up -d 一键起 16 个容器。

### Q74 测试有多少，怎么分层

> 71 个用例（10 个测试类：67 个纯单元 + 4 个集成）：纯单元覆盖切面、验证码、购物车、订单、Token 黑名单、缓存、事务监听器、搜索降级；集成测试用 embedded Redis 跑秒杀链路（避免 Testcontainers 与 Docker Desktop 兼容问题）。CI 跑 mvn verify 作为门禁。

### Q75 为什么不用 Testcontainers

> 它与当前 Docker Desktop 版本不兼容；Redis 集成测试改用 embedded-redis（注意用 com.github.codemonstur:1.4.0，旧的 ozimov 版本在 Windows 有内存映射错误）。随机端口用 new ServerSocket(0) 而非已移除的 SocketUtils。

## 九、开放设计题（拉开差距）

### Q76 ⭐ 让你从头设计一个秒杀系统，你怎么设计

> 按"前端-接入-应用-数据"讲：
> 前端：按钮置灰防连点、验证码、静态资源 CDN。
> 接入：CDN + Nginx，网关限流黑白名单。
> 应用：读多级缓存（本地+Redis），写走漏斗——动态路径、本地售罄标记、Lua 原子预减、MQ 异步；消费端加锁、DB 条件扣减、幂等表、失败补偿和死信。
> 数据：库存 DB 兜底，订单按用户分库分表；MQ 削峰。
> 保障：监控（各漏斗出口）、追踪、压测容量评估；一致性用最终一致 + 对账。
> 先问清楚规模（QPS、库存、预算）再给方案，体现工程权衡。

### Q77 热点商品怎么处理

> 商品详情和秒杀信息全缓存；库存热点 key 分片（一个逻辑库存拆成多个 key，请求随机命中，消费时汇总）+ 本地售罄标记；多级缓存读分担；结束后异步对账。

### Q78 如果要求"绝对不能少卖也不能超卖"

> 超卖靠 DB 条件扣减保证；少卖（成功者因异常没拿到订单）靠补偿和对账：定时比对已购标记与订单，缺单则补发消息或归还库存让用户重试，最终状态收敛。强一致成本高，用最终一致 + 可重试覆盖。

### Q79 100 个商品 100 万人抢，和 100 万商品 100 人抢，设计差异

> 前者是超高并发争抢极少库存，重点是漏斗拦截、热点 key 保护、削峰；后者是大规模数据检索，重点是分库分表、索引、搜索（ES）、缓存架构。瓶颈和方案完全不同。

### Q80 你怎么验证系统真的扛得住

> 先定容量目标，再用自研压测工具做并发档位扫描和优化前后对比；观察 QPS、错误率、CPU、队列堆积、Prometheus 指标交叉验证；找到瓶颈并验证改进有效。性能要靠测量，且压测环境要关掉干扰项（验证码/限流）单独测目标链路。
