## 1. 项目全景

### 1.1 这是个什么系统

mall-seckill 是一个**前后端分离的电商系统**，核心卖点是秒杀模块的高并发设计。业务闭环完整：

```
注册/登录(JWT) → 浏览商品(分类/SPU/SKU) → 加入购物车(Redis)
              → 下单(普通订单/秒杀订单) → 支付 → 发货 → 确认收货
                              ↓
                    超时未支付自动关单、回滚库存
```

## 3. 核心模块逐个讲

### 3.1 认证模块 security

**涉及类**：`SecurityConfig`、`JwtTokenProvider`、`JwtAuthenticationFilter`、`JwtProperties`、`TokenBlacklistService`、`CustomUserDetailsService`、`AuthController`。

**登录全流程**：

```
POST /api/auth/login (username,password)
  │
  ▼
UmsUserServiceImpl.login()
  1. 根据用户名查 ums_user（查不到 → "用户名或密码错误"，注意不暴露具体是哪个错）
  2. BCryptPasswordEncoder.matches(原始密码, 库里hash) 校验
     - hash 形如 $2a$10$xxxx，盐内置，每次加密结果不同
  3. JwtTokenProvider 生成两个 token：
     - access token  ：claims: sub=userId, type=access, username，短期
     - refresh token ：claims: sub=userId, type=refresh（无 username），长期
  4. 返回 LoginVO：access token 在响应体；refresh token 写入 Cookie
     Set-Cookie: refresh_token=xxx; HttpOnly; SameSite=Lax; Path=/; Max-Age=...
```

**为什么两个 token 分开存**（高频题）：

| | access token | refresh token |
|---|---|---|
| 有效期 | 短（分钟/小时级） | 长（天级） |
| 存储 | 前端内存（Pinia state，不写 localStorage） | httpOnly Cookie |
| 用途 | 每次请求放 `Authorization: Bearer xxx` | 仅调 `/api/auth/refresh` |
| 被窃后果 | 窗口短，风险可控 | Cookie 防 XSS 读取；SameSite 防 CSRF |

**JwtAuthenticationFilter 工作流程**（每个请求都走）：

```
请求进入
  1. 从 Authorization 头取 Bearer token，没有 → 放行（交给 Security 链，最终 401）
  2. JwtTokenProvider.validateAccessToken：验签 + 未过期 + type=access
  3. TokenBlacklistService 检查是否在黑名单（登出/轮换过的旧 token）
  4. 解析 userId → 构造 Authentication → SecurityContextHolder.getContext().setAuthentication()
  5. chain.doFilter（后续 @PreAuthorize / SecurityUtils.getCurrentUserId 才能拿到用户）
```

**RBAC 模型**（5 张表）：

```
ums_user ── ums_user_role ── ums_role ── ums_role_menu ── ums_menu
  用户         关联表           角色         关联表           菜单/权限标识
```

- 登录时 `CustomUserDetailsService` 查出用户的角色编码（如 `ADMIN`/`USER`）放入 `GrantedAuthority`
- 接口可用 `@PreAuthorize("hasRole('ADMIN')")` 控制（`@EnableMethodSecurity` 开启方法级鉴权）
- `/api/auth/info` 返回用户的角色与菜单，前端可据此渲染菜单/按钮

**主动登出**：登出时把当前 access token 的 MD5 作为 key 写入 Redis 黑名单，TTL = token 剩余有效期（见 `JwtTokenProvider.getRemainingSeconds`）。token 自然过期后黑名单记录自动消失，不无限膨胀。

**refresh 轮换**：`/api/auth/refresh` 用旧 refresh token 换新双 token，旧 refresh token 加入黑名单（`UmsUserServiceImpl.refresh`），防止 refresh token 被盗后无限重放。

### 3.2 商品模块 pms

- `PmsCategory`：分类，支持树形（parentId），`CategoryController` 返回 `CategoryTreeVO` 树形结构
- `PmsSpu`：标准化产品单元（如 iPhone 15），一个 SPU 有多个 SKU
- `PmsSku`：库存单元（如 iPhone 15 256G 黑色），有独立价格、库存、规格 JSON（specJson）
- `SpecTextUtil.toText()`：把规格 JSON 转成可读文本，落订单明细快照
- 商品详情：Caffeine L1 → Redis L2 → DB，带空值缓存防穿透（见文档二）

### 3.3 购物车模块 cart

- 存储：Redis **Hash**，key=`cart:user:{userId}`，field=skuId，value=CartItem JSON
- 功能：添加、改数量、删除、单选切换、全选、查列表
- `getSelectedItems()`：返回勾选商品——下单时商品只从这里取，**前端传的商品和价格一律不信**（防篡改）
- 价格实时来自 DB/SKU，购物车只存数量和选择状态

### 3.4 订单模块 order（见 `OrderServiceImpl`）

**普通下单 createOrder 八步**（这个要能完整复述）：

```
1. 幂等令牌一次性消费（Lua GET+DEL），防重复点击/网络重试
2. 取服务端购物车勾选项，空则拒绝
3. 批量加载 SKU/SPU，校验在售状态与库存；累加总金额
4. SQL 条件扣减库存：UPDATE pms_sku SET stock=stock-? WHERE id=? AND stock>=?
   影响行数 0 → 并发下库存不足，整单回滚
5. 落订单主表（订单号 "OD"+雪花ID，status=待支付, order_type=1）
6. 落订单明细（商品名/规格/单价全部快照！）
7. 清空购物车勾选项（在事务内，失败整单回滚）
8. 注册 afterCommit 回调：事务提交后才发延迟关单消息
```

**两个关键设计思想，面试必说**：

1. **快照**：订单明细里冗余商品名、规格、单价、图片。即使后来商品改名/改价/下架，历史订单展示和对账不受影响。
2. **先提交再发消息**：用 `TransactionSynchronizationManager.registerSynchronization` 注册 `afterCommit`，保证"事务回滚就不会发消息"，避免出现"用户收到关单通知但订单根本没创建"的脏消息。

**订单状态机**（`OrderStatus` 枚举）：

```
  待支付 PENDING_PAY
    ├── 支付 pay()           → 已支付 PAID
    ├── 用户取消 cancel()     → 已取消 CANCELLED（回补库存）
    └── 超时关单(延迟MQ)      → 已取消 CANCELLED（回补库存）
  已支付 PAID
    └── 后台发货 ship()       → 已发货 SHIPPED
  已发货 SHIPPED
    └── 确认收货 confirm()    → 已完成 COMPLETED
```

注意所有状态流转都是**条件更新（CAS 思想）**：

```sql
UPDATE oms_order SET status=? WHERE id=? AND status=?   -- 只有前置状态匹配才生效
```

例如支付：`payIfPending` 只有 status=待支付才能改成功，影响行数 0 就说明状态已变（被取消/已支付）。这天然防止并发下状态错乱。

## 4. 秒杀全链路逐行讲解（重中之重）

### 4.1 秒杀与普通下单的本质区别

普通下单：用户少、请求可以直接打 DB。
秒杀：**极短时间内流量是库存的成百上千倍**（如 1000 件商品 10 万人抢），直接打 DB 会被打死。所以核心思路是：**把请求分层拦截，越靠前的拦截成本越低，绝不让无效流量碰数据库。**

### 4.2 六级流量漏斗（简历核心，必须能默写）

对照 `SeckillServiceImpl` 类注释和 `execute()` 方法：

```
请求
 │
 ├─ 第0级（入口防护，在换路径阶段）
 │   图形验证码：挡住机器批量请求，验证码一次性消费
 │   动态MD5路径：真实下单地址开抢后才下发，防提前知道接口刷接口
 │   滑动窗口限流(@AccessLimit)：防同一用户/IP 高频连点
 │
 ├─ 第1级 本地内存售罄标记（execute 第309-314行）
 │   ConcurrentHashMap<seckillSkuId,true>，命中直接拒绝
 │   0 次网络 IO，纯 JVM 内存，成本最低
 │
 ├─ 第2级 预热缓存校验 + Redis Lua（execute 第316-341行）
 │   商品信息从 Redis 缓存取，不打商品库；校验时间窗口
 │   Lua 脚本一次 Redis 调用原子完成：一人一单判重 + 库存预减
 │   返回 -1 重复 / 0 售罄 / 1 成功
 │
 ├─ 第3级 MQ 异步下单（execute 第346-353行）
 │   预减成功才发 MQ，接口立即返回 QUEUING（排队中）
 │   MQ 削峰：把瞬时流量摊平成消费者能承受的匀速流量
 │
 ├─ 第4级 消费端串行 + DB 最终扣减（handleSeckillOrder）
 │   mq_consume_log 幂等
 │   Redisson 分布式锁：同一用户+商品的消息串行执行
 │   DB 条件扣减 UPDATE ... WHERE seckill_stock>=1（防超卖最终防线）
 │   订单/明细/秒杀订单三表落库（一个本地事务）
 │
 └─ 第5级 结果通知（registerAfterCommit）
     事务提交后写 seckill:result:{userId}:{skuId} = orderId
     前端轮询 result 接口：QUEUING / SUCCESS(orderId) / FAIL
```

**讲解金句**：
- "漏斗的设计原则是**成本递增**：内存拒绝 < Redis 一次往返 < MQ + MySQL 事务。让 99% 的请求在最便宜的层就被挡掉。"
- "库存有三道防线：Redis 预减挡住洪峰 → DB 条件扣减兜底防超卖 → 消费失败还有 Redis 补偿归还。"

### 4.3 三个秒杀接口的配合（前端时序）

```
① GET  /api/seckill/captcha              拿验证码图片(base64)+captchaToken
② POST /api/seckill/path/{seckillSkuId}  提交验证码 → 校验通过 → 返回 MD5 path
   （body: {captchaToken, captchaCode}）
③ POST /api/seckill/execute/{seckillSkuId}?path=xxx
   （body: 收货信息）→ 返回 {status: QUEUING}
④ GET  /api/seckill/result/{seckillSkuId}  定时轮询
   → QUEUING（继续轮询）/ SUCCESS+orderId / FAIL
```

**为什么要动态 path**：如果秒杀接口是固定的 `/execute/4`，脚本可以开抢前就不停打这个地址（甚至提前压测）。有了动态 path：① 必须先过验证码才能换到；② path 与用户+商品+盐做 MD5，别人猜不到；③ 有 60s 短 TTL，过期失效；④ execute 时按 `seckill:path:{userId}:{skuId}` 比对，不一致直接拒绝。

### 4.4 秒杀商品预热 uploadToRedis（管理端，第578-621行）

秒杀开始前由管理员触发，做三件事：

```
1. 组装 SeckillSkuCache（秒杀价、名称、图片、起止时间、限购数…）
   写入 Redis Hash：seckill:skus:{sessionId}  field=seckillSkuId  value=cache
2. 写两个索引/计数 String：
   seckill:stock:{seckillSkuId}        = 剩余可抢数量
   seckill:sku:session:{seckillSkuId}  = sessionId（execute 时先查它定位 Hash）
3. 清理动作：
   删除本地售罄标记 localSoldOutMap.remove(id)
   失效 Caffeine 中该场次 SKU 列表缓存（Cache Aside）
```

**为什么秒杀商品信息要全部放缓存**：秒杀期间商品信息读取量巨大，且这些信息（名称、价格快照）在秒杀期间不会变，放缓存让应用完全不打商品库。

### 4.5 秒杀消费端完整逻辑（第378-485行）

```
handleSeckillOrder(message) @Transactional
│
├─ 1. 消费幂等：mqConsumeLogMapper.tryConsume(messageId, queue)
│      INSERT IGNORE INTO mq_consume_log ...（messageId 唯一索引）
│      返回 0 → 这条消息处理过，直接 return（重复投递/网络重投）
│
├─ 2. Redisson 锁：lock:seckill:order:{userId}:{seckillSkuId}
│      tryLock(等待3s, 持锁10s)，拿不到 → "系统繁忙"抛异常
│      作用：同一用户的并发消息（理论上不该有，但兜底）串行
│
└─ doHandleSeckillOrder：
   3. 查 sms_seckill_order 是否已存在该用户+商品订单（业务判重，DB 层兜底）
   4. 从缓存读秒杀商品、从 DB 读真实 SKU/SPU（校验数据仍完整）
   5. DB 条件扣减秒杀库存：
      UPDATE sms_seckill_sku SET seckill_stock=seckill_stock-1
      WHERE id=? AND seckill_stock>=1
      rows=0 → 库存不足抛异常（这是防超卖的最终防线）
   6. insert oms_order（order_type=2 秒杀单，"SK"+雪花号，价格=秒杀价快照）
      insert oms_order_item
      insert sms_seckill_order（记录用户与秒杀商品关系）
   7. registerAfterCommit：事务提交后
      - 发延迟关单消息
      - 写 result key = orderId（前端轮询到成功）
      - 计 CONSUME_SUCCESS 指标（避免回滚导致指标虚高）
```

**注意幂等是三层**：mq_consume_log（消息维度）→ sms_seckill_order 查询（业务维度）→ 唯一索引 uk_user_sku（数据库最终约束）。

### 4.6 消费失败补偿（compensateOnConsumeFailure，第487-508行）

由 `SeckillOrderListener` 在捕获异常后调用：

```
1. 先查是否已落单（防止"重复投递的失败消息"把库存多加回去 → 库存虚增/超卖）
2. Redis 库存 +1：INCR seckill:stock:{skuId}
3. 从已购集合移除用户：SREM seckill:ordered:{skuId} userId
   → 用户可以重新参与抢购
4. 写 result key = FAIL（前端轮询到失败）
5. 清除本地售罄标记（库存回补了，可能从0变回1）
```

随后 Listener `basicNack(deliveryTag, false, false)`（requeue=false）→ 消息进 DLQ，由 `SeckillOrderDlxListener` 记录 x-death 原因并 ACK。

## 5. 数据是怎么流转的（库存视角）

以一件库存 100 的秒杀商品为例：

```
DB sms_seckill_sku.seckill_stock = 100
        │ 管理员预热 uploadToRedis
        ▼
Redis seckill:stock:{id} = 100
        │ 10万个请求涌入 execute
        ▼
Lua：前100个不同用户预减成功（stock 100→0），其余返回 0 或 -1
     stock=0 时本地售罄标记置位，后续请求 JVM 内存直接拒绝
        │ 100 条成功消息进 MQ
        ▼
消费者：每条 Redisson 锁 → DB seckill_stock 条件扣减 100→0 → 落单
        │ 全部成功
        ▼
DB 库存 0，100 张秒杀订单；result key 写入，前端显示成功
```

异常分支：

```
某消息消费时 DB 异常（如商品被误删）
  → 抛异常 → 补偿：Redis 库存还回去 + 移除已购标记 + result=FAIL
  → nack requeue=false → DLQ 记录 → 用户可重新抢 / 人工介入
```

## 6. 压测数据（必须会解释来源，详见 benchmark-report.md）

| 指标 | 数值 | 怎么测的 |
|---|---|---|
| 一人一单拒绝路径峰值 QPS | **921**（c=400） | 单用户高并发，全部命中 Lua 判重，每条 1 次 Redis 往返 |
| 售罄拒绝 QPS（本地标记 ON） | **1026** | 库存置0，纯内存拒绝 |
| 售罄拒绝 QPS（本地标记 OFF） | **476** | 每条都走 Redis Lua |
| 优化收益 | **2.16 倍** | 1026/476 |
| 成功下单同步 QPS | **738** | Lua 成功 + 发 MQ，返回 QUEUING |
| 消费 TPS（双实例） | **约 600** | 单实例 312 |
| 队列最大堆积 | **0** | 消费 ≥ 生产 |
| 错误率 | **0%** | — |

**环境**：本地 Docker，后端双实例各 `-Xmx384m`，Nginx 轮询；压测时关闭验证码和限流（避免测的是防护组件而非业务链路）；压测工具是自己写的 `scripts/SeckillBench.java`（Java 17 HttpClient）。

**面试诚实表述**："这是本地双实例的单机压测数据，不是生产集群。它验证的是架构的相对收益（2.16 倍）和瓶颈位置，绝对数值在生产硬件上会不同。"——这样说反而加分。

**瓶颈分析（压测报告第5节）**：
- 本地标记 OFF 时瓶颈是 Redis RTT；ON 时瓶颈转移到应用 CPU，证明优化有效卸下了 Redis 压力
- 消费端瓶颈是 MySQL 写入（行锁 + 多次写），生产可分库分表/批量插入/加消费者

## 7. 部署架构

### 7.1 docker compose 服务清单

| 服务 | 镜像 | 端口 | 作用 |
|---|---|---|---|
| mysql | mysql:8.0 | 3306 | 启动自动执行 sql/init/ 下 9 个脚本 |

| rabbitmq | rabbitmq:3.13-management | 5672/15672 | 消息 + 管理台 |
| zipkin | openzipkin/zipkin:3.4 | 9411 | 链路存储（默认内存） |

| nginx | nginx:1.27 | **8090** | 唯一对外入口 |
| prometheus | prom/prometheus | 9090 | 抓取后端 actuator |
| grafana | grafana/grafana | 3000 | 看板 |

- Compose 项目名固定 `mall-seckill`（硬约束）
- 启动：`docker compose up -d`；访问 http://localhost:8090；接口文档 http://localhost:8090/doc.html
- 默认管理员：admin/admin123

### 7.2 Nginx 职责（nginx.conf）

1. `root` 指向前端打包产物（容器内），托管 JS/CSS/图片
2. `location /api` 反代到后端 upstream（app1:8080/app2:8080 轮询）
3. `location /doc.html` 及 swagger 资源反代
4. `try_files $uri $uri/ /index.html`：SPA 前端路由刷新不 404
5. `keepalive` 长连接减少握手开销

### 7.3 本地开发模式

- 后端：`mvn spring-boot:run`（8080）
- 前端：`npm run dev`（5173，vite.config.js 把 /api 代理到后端）
